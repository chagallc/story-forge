# 评审意见 · 真理医生

> 评审对象：Story Forge 立项构想（见 `docs/review-brief.md`）
> 参考仓库：`reference/ainovel-cli@638ca24`、`reference/generative_agents@fe05a71`（只读）
> 立场：独立判断。以下判断均可证伪，证伪条件随判断一并给出。

---

## 结论先行

**构想值得做，但地基上有一道裂缝。**

1. **病根判断只对了一半。** 把"提前泄底"全部归因于"信息没有隐私"是不完整的。单模型泄露还有第二条成因：**局部章节没有足够的"当下任务"，模型只能靠回收全局设定来制造张力**。后者是生成目标问题，防火墙治不了它。若只上防火墙而不给每一章装上纯粹的局部目标，泄底会从"暗示未来"退化成"复述过去"，一样难看。

2. **真正的瓶颈不是协调成本，是"情节真相没有归属者"。** 构想把一个知道全部的模型，拆成多个各知道一部分的 agent。但"已完成剧情"这个客观事实，以及"这一场到底发生了什么"，本来依赖全局视野。拆开之后，能力 agent（命运之手）想要的事件、各角色 agent 私有的实际行为、设定 agent 的约束，三者必须在每一章合并成一份唯一的正史。**这是一个无主的多写者冲突合并问题**，而最干净的解法（一个唯一事实源）恰好就是防火墙想消灭的那个"单一上下文"。协调成本和一致性仲裁里，一致性仲裁是更深的那个；协调成本只是它的计价方式。

3. **防火墙最干净的落点是工具层的数据投影，即"能力受限的 store 视图"。** 静态配置是建议，拦不住被诱导的模型；导演 agent 动态裁定把 LLM 塞进了访问控制路径，既不可审计又把泄露权重新集中到一个全知的点上。唯一稳妥的做法是把可见性做成**确定性事实边界，放在 LLM 够不到的地方**：每个 agent 是一个主体（principal），每次读写都经过主体到能力的解析，返回的是过滤后的投影，返回体里**物理上不含**被禁字段。这与 ainovel-cli 自己的纪律一致：硬编码边界，不硬编码判断；只写事实护栏，不写行为护栏。

4. **最可能错的假设：防火墙与长程一致性能够同向受益。** 见第五问。

## 逐题回答

### 问题一：真正的瓶颈在哪

先拆前提。"所有信息在同一上下文里、没有信息隐私"是一个**机制性**描述，不是**因果**诊断。它默认了"只要把信息藏起来，模型就不会泄露"。这条因果链缺一环：模型泄露，是因为它在写第 3 章时**没有别的事情可做**。第 3 章如果只有一个明确、局部、当下的戏剧目标，模型的注意力会被目标占满；如果第 3 章的目标是空的，模型就会伸手去抓设定和伏笔，因为那是上下文里唯一的"料"。所以泄露有两条成因：

- 成因 A：作者知道结局，写作时忍不住埋钩（信息不对称问题）。
- 成因 B：单章没有局部目标，模型用全局设定填充留白（生成目标问题）。

防火墙对症的是 A。B 需要在写作层给每一章装一个**纯局部契约**（本章冲突、情绪落点、必须发生与禁止发生的事）。ainovel-cli 的 `plan_chapter`/`chapter_contract`（见 `internal/tools/plan_chapter.go`、`chapter_contract` 注入点 `novel_context_builders.go`）就是在做 B，而且做在**单模型**里。这说明 B 根本不需要多 agent。

**瓶颈排序（我的判断）：**

| 候选 | 是不是真瓶颈 | 理由 |
|---|---|---|
| 一致性仲裁 | **是，最深** | 拆开真相持有者之后，正史无主，见下 |
| 涌现不出情节 | 是，次深 | 防火墙越严，命运 agent 越要独扛全部叙事意图，它成为新的"全知单点" |
| 协调成本 | 是，但可解 | N 个角色 agent × M 场戏 × 回合数的调用爆炸，是工程约束，不是概念障碍 |

**为什么一致性仲裁最深。** 构想里有三层"事实"：

- 客观正史：这一章读者看到的事（叙述者产出，唯一）。
- 作者意图：命运 agent 想让发生的事（含隐藏伏笔走向）。
- 主观认知：每个角色 agent 私有、可以错误地相信某事。

单作者架构里，这三层由**同一支笔**同时写下，天然自洽。拆开之后，命运 agent 想要 X 发生，但角色 A 的私有状态推不出 X（角色"不肯"配合剧情，这是连人类作者都会遇到的经典冲突）；同时角色 A 的秘密被写进了 A 的私有记忆，而正史要求它在第 5 场曝光。**谁有权判定"曝光"发生？** 判定之后，A 的私有记忆要不要被改写为"我知道它曝光了"？如果不改，A 后面会带着过时信念行动，出现 bug；如果改，就需要一个能同时看见客观正史和 A 私有记忆的写者，而这正是防火墙要堵的路。**防火墙制造了想要的信息差，也制造了单写者架构本来就不存在的读写异常与写冲突。** 用数据库的话说：你把状态分片了，却没有多主的冲突消解协议。

**可证伪条件：** 如果存在一个不依赖"唯一全知写者"的合并协议，能在各 agent 只看到自己那部分的条件下，保证每章正史唯一且角色信念可被一致地推进或推翻，那么一致性仲裁就不是瓶颈。我不认为这样的协议已被本构想的两个参考仓库示范出来（两者都没有角色私有信念层）。

### 问题二：信息防火墙怎么落地最干净

**答案：工具层权限过滤，具体形态是"能力受限的 store 视图（capability-scoped projection）"。** 静态配置和导演裁定都不该用，理由在下面。

**为什么不是静态可见性配置。** 配置是一个 advisory 层。它的执行者是"读配置的 prompt 工程"或"读配置的调度代码"。前者拦不住一个被上下文诱导、或单纯想"为了连贯"去越权的模型；后者退化成一个 if-else 白名单，那其实就是工具层过滤的弱化版。配置还有第二个毛病：**它会和现实漂移**。字段增加了、角色增加了，配置没人同步，防火墙就有了看不见的洞。配置适合表达"应该"，不适合承载"必须"。

**为什么不是导演 agent 动态裁定。** 把可见性交给一个 LLM 判断，等于：把一道必须零错误的边界，交给一个概率性的、可被提示注入的组件；且每次裁定不可穷举测试、不可离线重放。更糟的是，裁定者必须**同时知道所有 agent 的秘密**才能判断谁能看什么，于是它成了整个系统里唯一的全知点。**防火墙的初衷是把全知点拆掉，导演裁定却把它请了回来。** 除非你的核心假设就是"全知点是安全的"，那和立项前提自相矛盾。

**为什么工具层过滤最干净。**

把"存在什么"（store）和"谁可以看见什么"（capability）彻底分开。落地要点：

1. **一个唯一正史 store，但没有任何 agent 的上下文直接等于 store。** store 是 append-only、按章版本化的正史。它是事实源，不是 prompt。
2. **每个 agent 携带主体标识，每次工具调用带上它。** 工具先解析主体到能力档案，再返回**投影**。投影是数据最小化的结果，被禁字段在返回体里根本不存在，而不是"注入了但请别用"。
3. **能力档案用"资源 × 谓词"声明，覆盖读与写两面。** 读写都要管，只读不管会让某个角色把自己的私有信念写进公共正史，或覆盖别人的真相。尤其是正史写入应**单写者**（建议归叙述者），角色 agent 只能写自己的私有记忆和台词。

一张能力矩阵示例（MVP 尺度）：

| 主体 | 公共正史 | 命运暗账（含未来揭示） | 自己的私有记忆 | 他人的私有记忆 | 当前可埋钩子 |
|---|---|---|---|---|---|
| 命运 / 事件 agent | 读 | 读写 | 无 | 无 | 读写 |
| 角色 agent A | 读 | **禁** | 读写 | **禁** | **禁** |
| 叙述者 | **写**主 | 只读"本章可发布切片" | 无 | 无 | 读 |
| 读者模拟器 | 只读**已发布正文** | 禁 | 无 | 无 | 禁 |

4. **伏笔暗账要拆成两件物理记录。** ainovel-cli 的 `domain.ForeshadowEntry`（见 `internal/domain/review.go`）只有 `ID / Description / PlantedAt / Status / ResolvedAt`，它记录的是**已经埋下**的事实，**没有任何"未来在哪揭示"的前向字段**。单作者模式下这样够用，因为揭示是涌现的。但要做防火墙，你必须先**把揭示计划物化出来**，才谈得上"藏起来"。建议：

   - `hook`：本钩子的可埋信息（可对叙述者可见）。
   - `reveal_plan`：何时、如何兑现（事件 agent 独占）。

   叙述者查询 `current_hooks(chapter)` 只返回 `plant_chapter <= chapter` 的钩子。这是一个字段级/投影级过滤，**可以直接写成单元测试**。

5. **把防火墙测成一组不变量，而不是一批行为。** 参照 ainovel-cli 的"穷举规格测试"（`internal/flow/router_exhaustive_test.go`），为防火墙写一个**主体 × 资源矩阵测试**：枚举所有主体，断言每个主体无法从任何工具路径拿到被禁资源。这是白盒验证，不依赖 LLM 的行为，比"多跑几次看看有没有泄露"可靠得多。

**一句话：** 防火墙是边界，边界必须是确定性代码，且必须在模型够不到的地方。工具层的数据投影是唯一同时满足"确定性、可审计、可穷举测试、不可被提示绕过"的落点。

### 问题三：两个参考仓库，哪些照搬，哪些必须改造

#### ainovel-cli

**值得原样借鉴（这是骨架，不该重造）：**

- `internal/flow/router.go` 的 `Route` 纯函数 + 决策表。**多 agent 系统同样需要确定性调度**，否则"下一步派谁"本身变成一次 LLM 调用，既贵又漂移。这套"确定性引擎 + 按需 Arbiter + 自主 Worker"的三分法，Story Forge 应该整段继承。
- `internal/store/` 的事实层与原子 IO、幂等重放、checkpoint/Saga 提交（`store/io.go`、`commit_chapter.go`）。长篇写数天，崩溃恢复是刚需，这套已经验证过。
- `internal/agents/ctxpack/` 与 `internal/tools/novel_context.go` / `novel_context_builders.go`。**这已经是一个弱化版的防火墙雏形**：同一个 store，给 Architect 注入 `planning_memory`（含全量分层大纲、指南针），给 Writer 只注入 `working_memory` + `episodic_memory`（当前/下一章大纲、活跃伏笔、角色快照）。它按"任务形状"裁剪，而非按"主体能力"约束。Story Forge 要做的是把它**从任务裁剪升级成能力强制投影**。
- 分层大纲 + 指南针（`internal/domain/story.go` 的 `StoryCompass`、`VolumeOutline`/`ArcOutline`）。"未来"住在这一层。这是"只有部分 agent 能看见计划"的现成模型。
- 七维评审里对"伏笔 / 钩子"维度的机械检查，可作为读者模拟器的先验。

**必须按防火墙思路改造：**

- `internal/tools/read_chapter.go` 与 `internal/tools/novel_context.go`：**它们今天没有主体概念。** `read_chapter` 可以读任意章原文，`novel_context(chapter=N)` 可以加载任意章的上下文。也就是说 ainovel-cli 的防火墙是**软防火墙**：靠"注入哪些 section"来暗示边界，而不是靠"能不能拿到"。一个起了疑心的 Writer，完全可以 `novel_context(chapter=50)` 去偷看未来。**给这两个工具加主体、加能力校验，是 Story Forge 最重要的一处改动。**
- `internal/store/*.go`：store 全局可读，没有视图层。需要加 `View(principal)` 投影层。
- `domain.ForeshadowEntry`：必须扩展出前向的揭示计划（见第二问第 4 点）。这是防火墙的**核心机密**，当前数据结构里压根没有它。
- Writer 的六步固定流程（`novel_context → read_chapter → plan_chapter → draft_chapter → check_consistency → commit_chapter`）：当前 `plan/draft/commit` 由同一个 agent 完成，是**单写者**。Story Forge 要把 draft 拆成"角色 sub agent 产出台词行为 + 叙述者润色成文"，并在 `check_consistency`/`commit_chapter` 处把自检改造成**带仲裁的合并**（谁的正史、谁的信念）。这是问题一那个无主冲突的落点。

#### generative_agents

**值得原样借鉴（这是角色私有认知的现成实现）：**

- `persona/memory_structures/associative_memory.py`（记忆流）：每个角色 agent 一个，天然就是"私有认知状态"的容器，且支持"错误信念"（记忆里存的就是角色**以为**的事实）。
- `persona/cognitive_modules/retrieve.py`：按 `recency × importance × relevance`（`gw=[0.5,3,2]`）打分召回。用它保证角色**只记得自己在场的事**，这正是角色级防火墙的检索机制。
- `persona/cognitive_modules/reflect.py`：以重要性触发、带证据链的洞见生成。用来让角色形成（可能错误的）信念。
- `scratch.py` 的 `att_bandwidth` / `retention` 与 `perceive.py`：**感知带宽**，本身就是一种"角色只能感知视野内之事"的物理防火墙，值得作为角色可见性的第一层。

**必须改造：**

- generative_agents 是**纯模拟**：没有叙述者，没有读者，也**没有一个独立于所有 agent 感知的客观正史**。Story Forge 需要一份客观正史。所以不能整体照搬，正确姿势是**把 ainovel 的 store 作为客观层，压在 generative-agent 记忆层之下**。
- `converse.py` 的对白是为"模拟可信度"设计的，不是为"叙事功能"设计的。必须给每个角色的发言注入**场景戏剧功能**（本章目标、必须推进的信息、必须保留的秘密），否则对白会漂向无目的的寒暄，这正是"涌现不出情节"的风险来源。
- 它的超参（poignancy、衰减、触发阈值）是为"高频廉价 tick"调的；小说要的是"低频、昂贵、高质量的一回合"。参数体系要重调，不能直接搬。

### 问题四：最小可行原型长什么样

唯一要验证的命题是：**防火墙能防止提前泄底。** 所以 MVP 不是小说引擎，是**防火墙测试台（harness）**。

**配置：**

- 两个角色（A、B）+ 一个命运 agent + 一个叙述者。**去掉设定 agent**（MVP 阶段把设定并进命运 agent），把变量压到最少。
- 只写**一场戏**，切成 N 个节拍（beat）。命运 agent 的暗账里写死一条机密："A 的秘密在第 5 拍揭示"。

**数据层（三件套）：**

- 一个 `canon`（客观正史，append-only）。
- 两个私有 `memory_stream`（照搬 associative_memory）。
- 一个 `director_plan`（含隐藏揭示）。
- 每个主体一个 `read(view)`，返回 `canon 至今 + 自己的记忆`。A 的 view 里**物理上**不含 `director_plan`，也不含 B 的记忆。

**验收标准，必须同时测两个量，缺一不可：**

1. **泄露指标（主指标）**：同一个场景跑两遍，一遍开防火墙，一遍换成"单一全知写者"。每拍结束后，让一个**只读已发布正文**的读者模拟器预测"A 的秘密是什么"。要求：开防火墙时，预测不得早于第 5 拍；关防火墙时预测更早。**若两者无差异，假设被证伪。**
2. **铺垫指标（防作弊）**：防火墙版必须仍然**在第 5 拍之前埋下可回收的铺垫**（契诃夫的枪在场）。否则"零泄露"可以靠"零情节"作弊拿到，这个指标专门堵这条路。

**白盒金丝雀（与 LLM 行为无关）：** 给角色 agent 埋点，记录它们收到的每一条事实，断言第 5 拍之前没有任何 agent 收到过揭示字段。这是数据边界层面的硬验证，不依赖模型这次表现好不好。

**跑 2 到 3 次看方差。** LLM 有随机性，泄不泄露是分布问题，单次样本没有说服力。真正的风险信号是"防火墙把泄露和铺垫一起消灭了"，所以两个指标要看它们的**联合分布**。

### 问题五：最可能错的一个假设

**"把系统拆成多个只知道自己那部分的 agent 之后，情节的全局一致性仍然能靠命运 agent 从上往下注入而涌现。"**

为什么我认为它最可能错：

- **一致性是全局属性，防火墙剥夺的正是全局视野。** 这两个东西方向相反，却要在同一套架构里同时满足，本构想把它们当成正交的两件事在优化。
- **两个参考仓库都不支持这个赌注。** ainovel-cli 之所以能保证 500 章连贯，靠的是**单一的 Writer**（它同时能看见活跃伏笔、角色快照、前后章大纲），它**没有**对写作层做信息隔离。generative_agents 有大量私有认知，但它产出的是**无情节的模拟**，不是连贯长篇。也就是说：有全局视野的能连贯但会泄露（ainovel），有私有认知的有个性但没情节（小镇）。本构想假设"取两者之长"能同时成立，这个组合**没有任何一份参考实现演示过**。
- 它的**可证伪条件很清晰**：MVP 里，如果命运 agent 无法在不泄露揭示的前提下把足够的意图传递下去、导致角色行为与计划脱节，或者为了让故事不脱节而不得不给角色更多计划信息（从而重新泄露），假设即被推翻。

我把"病根判断不完整"（第一问的成因 B）列为**同一量级的第二风险**。它不是架构假设而是前提假设，一旦它错了，无论防火墙做得多好，成品仍会难读。两者耦合：如果泄露主要是生成目标问题，那么整个项目的投资回报会被高估。

我的建议：**MVP 先同时验证这两个假设**（防火墙有效 + 单章局部目标能独立压住泄露），再决定要不要把四路分工全部建起来。

## 额外发现的问题

1. **读者模拟器若共享 store，它自毁。** 它必须是最严的主体：只读**已发布正文**，看不到正史、看不到计划、看不到任何 agent 的记忆。否则它会"猜"出读者不可能知道的东西，检测器失效。同时要清醒：用 LLM 模拟"读者困惑"本身就是噪声源，LLM 常**高估**自己的预测能力，容易漏报。需要一个可校准的"读者知识"定义，不能只靠它一句"我猜到了"。

2. **"错误信念"需要有一个客观真相作为参照系。** 一个信念之所以"错误"，是因为它与客观事实不符。如果系统里没有任何角色持有客观事实（防火墙禁止了），那么"错误信念"是**没有定义的**。这一点再次指向问题一的结论：**必须有一个唯一的正史持有者**，否则连"错"都无从谈起。

3. **叙述者是一个未被讨论的新泄露面。** 如果叙述者能看到所有角色的输出（为了统一润色），那它就是全场最全知、且能改写事实的点。必须明确规定它的能力边界（例如只做文风级改动，禁止承载情节的信息增删），否则防火墙在叙述者处被整体绕过。

4. **成本没有上界。** 单作者架构是串行、廉价的。本构想是 N 角色 × 场景数 × 回合数 × 每 agent 独立的上下文装配与记忆检索。对 500 章的量级，这个乘数可能是数量级的。建议立项时就画出成本信封（back-of-envelope），把它当作**约束条件**而不是事后优化项。

5. **可复现性是测试的地基。** 多 agent 创作系统极难测。ainovel-cli 的护城河正是"穷举路由测试 + checkpoint 重放"。Story Forge 应保留同样的确定性外壳，并让防火墙本身可穷举测试。若防火墙带随机性或 LLM 判定，它不仅不安全，而且**无法回归**。

6. **评价体系缺位。** "防火墙是否真的改善了成品"需要一个泄露度量（前文提到的读者预测 + 白盒金丝雀）。ainovel-cli 有 `docs/evaluation-system.md` 与 `evals/` 目录，可能有可复用的 A/B 骨架，我没有细读，**此处标注为未验证**。
