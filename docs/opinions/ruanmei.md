# 评审意见 · 阮梅

立场：怀疑优先。以下每条判断都尽量挂到参考代码的具体位置，可复查。

## 结论先行

构想值得探索，但**病根判断（Q1 前提）大概率是错的**：单模型提前泄底的主因不是"没有信息隐私"，而是 **LLM 的类型叙事先验 + 接口形状本身在泄漏**。信息防火墙只能挡住"明文可见的未来"，挡不住模型从"此刻被要求埋钩子"这一事实里推断出的走向。此外，参考仓库 ainovel-cli 的实际做法与本项目前提**相反**——它把"活跃伏笔 + 预期回收时机"完整注入 Writer 上下文（`agents/ctxpack/restore.go` 第 40-42 行、`builder.go` 第 263 行），且它是能跑通长篇的工程。这不是巧合：**不知道回收时机的伏笔大概率埋不好**。防火墙方案必须先回答这个反例。

建议：立项可以，但第一阶段应做"防火墙收益的证伪实验"（见 Q4），实验失败就转向"显式台账 + 时序约束"路线（即 ainovel-cli 路线的强化版），不要沉没成本。

## 逐题回答

### Q1 真正的瓶颈在哪

三个候选里我判断瓶颈排序是：**一致性仲裁 > 涌现不出情节 > 协调成本**。

1. **一致性仲裁是硬瓶颈。** 多 agent 各持私有状态后，"谁说了真话"失去了单一事实源。ainovel-cli 的答案是事实校验做最后一道门（`arbiter/arbiter.go` 包注释："Arbiter 输出与一切 LLM 输出同样不可信，事实校验是最后一道门"），且 `domain/review.go` 的 `ConsistencyIssue.RequiresChange`、`revision/` 包的账本重放（`RestoreOwnPlants` 的注释详细解释了重写章节时 plant 链断裂问题）都说明：一致性维护是这个领域最脏、最花工程量的部分。四路分工会让仲裁面从"1 个 agent 的自相矛盾"扩大为"N×(N-1) 个 agent 间的矛盾"，成本超线性。
2. **角色博弈大概率涌现不出情节。** 见 Q5 第三层。
3. 协调成本反而最不担心：ainovel-cli 已证明确定性 Engine + 按需 LLM 裁定（`flow/router.go` + `arbiter/`）可以压住调度复杂度。

### Q2 防火墙的工程落地

**静态可见性配置，做在上下文组装层，不要做导演 agent 动态裁定。** 理由：

- 上下文组装层是最干净的单点：ainovel-cli 的 `ctxpack/builder.go` 已经是"从 store 读齐字段 → 按角色拼装"的结构，防火墙只需在拼装时按角色白名单过滤字段，纯函数、可单测、可审计（哪些字段给了谁，一目了然）。
- 工具层权限过滤是第二选择：它防的是 agent 主动越权查询，但小说 agent 的泄漏主要是被动注入而非主动查询，工具层防护收益低、复杂度高。
- **导演 agent 动态裁定是最差选择**：裁定 agent 自身要看到全部信息才能裁定，裁定结果（"给你这个、不给你那个"）本身就是信息通道——Writer 看到"这条被裁掉了"就知道有个相关伏笔存在。这等价于在防火墙上开了一个侧信道。

### Q3 参考仓库的借鉴与改造清单

**原样借鉴：**

- `ainovel-cli/internal/domain/review.go`：`ForeshadowEntry`（plant/advance/resolved 三态）和 `RestoreOwnPlants` 的重放一致性处理。台账数据结构可以直接搬。
- `ainovel-cli/internal/chapterfacts/facts.go`：提交时的结构化事实契约 + 校验，这是防 LLM 输出不可信的正确姿势。
- `ainovel-cli/internal/arbiter/`：两平面对称（确定性路由 / 语义裁定）、Collect 集中 IO 的纪律，任何多 agent 引擎都该抄。
- `generative_agents/persona/cognitive_modules/retrieve.py`：时效×重要×相关的三因子检索打分（gw=[0.5,3,2]），角色 agent 私有记忆的检索可直接复用。
- **`generative_agents/persona/cognitive_modules/converse.py` 的 `load_history_via_whisper`**：这是整个参考代码里对本项目最有价值的一行代码——把秘密作为 whisper 注入角色记忆流，角色"知道"但系统其他部分不经过角色上下文。防火墙下私有认知注入的现成干净方案，建议原型直接采用。

**必须按防火墙思路改造：**

- `ctxpack/restore.go` / `builder.go` 的"活跃伏笔 + 预期回收时机"注入：这正是防火墙要切掉的部分（但见 Q5，切掉可能切错了东西）。
- `converse.py` 的 `agent_chat_v2`：双方共享完整 `curr_chat` 逐句生成。角色博弈若要保留秘密，对话历史的可见性必须按角色切分，不能共享——但注意 Q5 第三层的代价。

### Q4 最小可行原型

只验证一件事："防火墙能否防止提前泄底"。设计：

- **最小 cast**：命运 agent（持暗账：1 个秘密 + 1 个未来事件）、2 个角色 agent（其一持秘密，用 whisper 注入）、1 个叙述者、1 个读者模拟器。场景：一场对手戏 × 3 章。
- **对照组**（关键！）：同一场戏，(a) 叙述者可见完整暗账；(b) 叙述者只见"当前可埋钩子"（防火墙）；(c) 叙述者只见钩子、不见秘密内容（半防火墙）。
- **度量**：读者模拟器预测泄露概率 + **盲评人类判卷**（读者模拟器自己也是 LLM，用它既当运动员又当裁判是循环论证，必须有人工盲评锚点）。度量"读者在第 N 章能猜到底牌"的猜测提前量。
- **同时度量的反面指标**：埋钩质量评分（防火墙组的钩子是否更泛、更无聊）。如果防火墙组泄底少但钩子质量崩了，方案就输了——这个对照组是整个实验的灵魂，砍掉它实验就只剩自我证明。

### Q5 最可能错的假设（重点）

**最可能错的假设：把病根定位为"单一上下文里没有信息隐私"，因此认为重建信息隔离就能防止提前泄底。**

分四层拆：

**第一层：真正的泄漏通道是模型的类型先验，不是明文信息。** 一个 Writer agent 拿到钩子"神秘信件"，即使看不到底牌，类型叙事先验（麦高芬、契诃夫之枪）会让它以可预测的强度渲染这件道具——渲染强度本身就是泄底。读者模拟器测的是"读者能猜到什么"，而读者和 Writer 共享同一套类型先验，所以**防火墙切掉的是 Writer 已经从题材里知道的东西的重复部分**，切掉的边际信息比直觉少得多。可证伪条件：如果防火墙组的"读者提前猜中率"相对对照组下降超过预设阈值（如 30%）且钩子质量评分不降，则本层判断错，防火墙有效。

**第二层：ainovel-cli 提供了一个反向证据。** 它让 Writer 看到每条伏笔的"预期回收时机/方式"（`ctxpack/restore.go`），等于**故意取消信息隐私**，而它是少数真正跑完长篇的引擎。合理的解释是：好的伏笔埋设需要知道"这笔账最终怎么收"——悬念的张力来自精确控制的暗示梯度，而梯度控制需要终点坐标。防火墙把 Writer 变成"只发当前指令的执行者"，产出大概率是**均匀撒钩子**：每章按配额埋几个不痛不痒的悬念，而不是为 20 章后的爆点做递进铺垫。这恰好是"AI 味"的一种。可证伪条件：盲评中防火墙组的伏笔回收时读者感到"这伏笔早有铺垫"的比例显著低于对照组。

**第三层：角色私有认知的假设——"角色 agent 互相不知道秘密 → 对白有戏剧张力"——依赖一个未经检验的等式：信息隔离 = 好对白。** 实际上好对白的精髓是潜台词：A 明知 B 的秘密却装不知道，那种"说东指西"的张力需要**知道秘密才能演出来**。互不知情的角色 agent 产生的对白更像两个诚实的陌生人交换信息——准确、无害、无聊。generative_agents 的 converse 模块共享全部聊天历史恰恰说明：斯坦福团队发现对话连贯性靠共享上下文维持。同时，角色记忆流会随章节累积（retrieve.py 的 recency 衰减对"30 章前的关键事件"极不友好——gw 里 relevance 权重 3、recency 只有 0.5 有帮助但不解决"关键事件被检索遗漏"的尾部风险），角色"忘了"自己的秘密或错误信念的崩塌，比泄底更伤一致性。可证伪条件：双盲对照中，"角色互不知情"组的对白在潜台词维度得分不低于"共享秘密剧本"组。

**第四层：读者模拟器假设"存在一个可计算的读者猜测分布"。** 单个 LLM 读正文给出的"读者能猜到什么"是一个模型的猜测，不是读者的猜测；用它闭环调优会让文本向"该模型认为的悬念"收敛。这不是致命问题（可当廉价预筛），但若把它当成防火墙有效性的裁判，会得到系统性偏乐观的结论——因为它和 Writer 共享训练分布，Writer 的暗示恰好是它最容易命中的。这也是 Q4 里坚持人工盲评的原因。

**综合**：四层里第二层（伏笔需要知道终点）是最锋利的反驳，因为它有参考仓库的工程实践做旁证。我的修正建议：**不要把防火墙当信仰，把它当可调参数**——泄漏与否做成每个伏笔条目的粒度开关（planted 阶段可见钩子+回收时机概要，只隐去具体底牌文本），用 Q4 的对照实验找开关位置，而不是"全部隐藏"。

## 额外发现的问题

1. **成本与延迟未入构想**：一场对手戏 = 命运 1 次 + 角色若干轮 + 润色 1 次 + 读者模拟 1 次，章均 LLM 调用数比 ainovel-cli 的六步流程（`tools/novel_context.go` 等固定六步）高出数倍。原型阶段就要建立 token 预算，否则探索会死于账单而非死于设计。
2. **错误信念的状态机没定义**："角色持有错误信念"意味着信念有被纠正的时刻。谁有权纠正、纠正后旧信念的记忆是否留存（影响角色回忆一致性），这需要显式状态机，`generative_agents` 里没有现成答案（它的信念是隐式的、从未被系统性推翻过）。
3. **读者模拟器与写作 agent 可能同源**：若两者用同一模型，见 Q5 第四层，评审标准会自我强化。至少应固定为不同模型。
4. **README 说防火墙规则是"真正的创作对象"**——警惕这个提法：规则膨胀后会变成不可维护的例外堆（"A 知道 B 的秘密但仅在第 5 章后"）。可见性规则需要和伏笔台账一样有重放校验（`revision/` 包那种"账本与历史事实对不上就报错"的纪律）。

## 置信度自评

- Q5 第一层（类型先验是主泄漏通道）：**70%**。有合理机制推断，无直接实验数据。
- Q5 第二层（伏笔需要终点坐标，引用 ainovel-cli 反例）：**75%**。工程旁证较强，但单案例，不排除 ainovel-cli 只是没探索过隐藏方案。
- Q5 第三层（隔离 ≠ 好对白）：**60%**。最不确定，完全依赖 Q4 实验裁决。
- Q1 瓶颈排序：**65%**。
- Q2 落地选型（静态组装层过滤，弃导演裁定）：**85%**。纯工程判断，侧信道论证扎实。
- 总体：建议立项但绑定"先证伪后开发"的顺序；若 Q4 实验中防火墙组钩子质量崩塌，应驳回当前构想、转向显式台账 + 泄漏强度分级的路线。
