# story-forge 战略评议（Morgan · 女王型战略顾问）

> 评议日期：2026-11-04 · 依据：台账全程 + v2 蓝图 + 决策 0001-0005 + M1/M2 变更说明
> 健康度：**黄灯 6/10**——不是濒死，而是到了必须停止堆能力、开始接受真实连载审判的阶段。

## 总裁定

**项目继续，核心方向不改。但已经从「验证核心假设」滑向「建设一套看起来完整的写作系统」。**

技术方向有价值，工程纪律明显高于一般 AI 写作项目；但产品证据严重落后于架构复杂度。防火墙、章节卡、状态机、投影、检测器都在增长，真正决定生死的证据却仍然缺失：

> **一个真实作者，能否用它稳定写到 10 万字，并获得优于普通单模型工作流的留存、质量与效率？**

目前不能回答。

| 维度 | 裁定 |
|---|---|
| 核心洞察 | 强 |
| 实验设计能力 | 强 |
| 工程实现 | 中上 |
| 长篇架构 | 可行，但已有裂缝 |
| 产品验证 | 弱 |
| 人力可持续性 | 高风险 |

## 一、方向判断

**终局价值不该是「多智能体写小说」**——太容易被复制。story-forge 真正可能形成壁垒的，是一套**受约束的长篇叙事生产系统**：

1. 管理谁在什么时候能知道什么
2. 把创作意图、已发生正史和本次生成上下文分开
3. 让正文修改能够安全回灌人物认知、伏笔和世界状态
4. 让作者控制关键选择，而不必手工维护整部小说的一致性

终局产品是：**长篇小说的版本控制、信息权限系统和叙事状态机。**模型会更换，提示词会贬值，检测器会失效；正史提交、角色认知、信息投影、修订传播和作者决策链才是耐久资产。

**「先证伪后开发」前半程合格，后半程偏离**：三臂对照、金丝雀、异构读者、人工盲评并用、接受反证——真正的实验纪律。但决策 0001 的证伪协议（exp003 正式批次、五次重复、异构裁判、防火墙甜蜜点标定）至今未完成，角色 sub-agent 第二阶段未展开；与此同时动机层、开场契约、润色、工作台、章节卡、状态提交、认知系统、上下文投影已连续建设。**核心假设只获得了方向性支持，尚未完成原定证伪协议；工程却已经按「假设成立」继续扩张。**

**检测器对抗已被证伪**：检测器互相矛盾、低 AI 分可能对应更差叙事、所有主力模型都可能在某个检测器下失败、平台真实反馈来自读者编辑和追读数据。继续优化检测器通过率不再是产品主线——冻结为风险提示。

## 二、架构健康度

三层权威方向正确，但三个裂缝：

**裂缝一：章节卡双副本**（card.json + bible.meta.card）。建议 card.json 为唯一权威，bible 只保存路径/摘要/版本号/内容 hash。

**裂缝二：commit 不是跨文件原子提交**。canon→state→card→bible 的顺序任何一步中途失败都会分叉。M3 前必须补：commit manifest / transaction journal；prepare→validate→apply→finalize 状态机；启动时检测未完成事务；四方 revision/hash 对账；可恢复可回滚。

**裂缝三：语义权威不完整**。角色遗忘、误认、谣言与事实区分、信息过期、物品转移、身份伪装、公开/私下双重关系——如果靠自由文本维护，state 会退化成「部分可信的提示材料」。不要急着加几十种 op：先用真实连载采集状态变化类型，再扩 reducer。

**M3 被低估，拆成两个**：M3A 滚动连载（连续写到 10 万字）/ M3B 修订传播（旧章修改、依赖失效、差异审计、回滚）。「后续章节标 stale」只是贴警告标签，不是依赖传播系统。

**「机器管结构、人管文字」边界正确，但人类工作量没被当作硬预算**。当前工作流作者要参与：分支选择/深入讨论/锁卡/审草稿/修正文/审 DELTA/commit/lint 豁免/盲读终审——作者可能变成系统唯一的整合器和事务管理员。应记录：每章总耗时/人工操作时间/改稿时间/管理时间/首稿保留率/卡到正文偏移率/无 story-forge 对照耗时。**没有「作者分钟/千字」就没有生产力结论。**

## 十万字规模碎点排序

1. 修订传播（无完整闭环）
2. 人工审批积压（流程纪律反噬创作欲望）
3. 投影失真（固定截取→需因果/人物/伏笔/地点相关性+作者钉选）
4. 状态抽取静默遗漏（该写入的没写入比错误写入更危险——需遗漏检测）
5. 章节卡僵化（建议三档：轻章最小卡/标准章/高风险章完整卡）

## 三、最大风险

1. **头号死亡路径：做成优秀的实验系统，却没有人愿意长期使用**——机制比竞品先进、测试全绿、真实小说仍写不出来，或作者回到普通聊天窗口写正文。
2. 检测器对抗是已证伪支线——继续优化会牺牲可读性、过拟合单一检测器、制造虚假确定性。
3. ZCode 外包会产生「合同通过、系统退化」——工单内通过≠权威边界不漂移≠异常可恢复≠作者愿意用。多份「工单未写明的裁决」累积会让架构控制权转移到交付者局部判断。**责任落名：ZCode 管工单内实现；Hana 管架构一致性/异常路径/跨里程碑回归；月华管真实使用价值与文字终审。**
4. 人类作者兼任设计者/终审者/唯一用户——个人偏好会被误当市场规律。Webnovel 实测要引入非参与者盲读+真实平台数据+留存/评论/改稿成本记录。

## 四、资源排序

1. **英文 Webnovel 真实验证（50-60%）**：最小真实连载批次——题材贴合 Webnovel、12-15 章、3-5 万词、普通 GPT 工作流对照、记录作者分钟/千字/首稿保留率/返工率/追读评论信号、预先定义停损线。**如果真实连载跑不动，就不应该继续扩 M3。**
2. **M2 验收与最小必要修补（25-30%）**：专打异常路径——commit 中途失败恢复、四方 revision 对账、delta 遗漏检测、投影双模式成文质量差异、连续 20-30 章状态漂移、人工修订 stale 传播。验收后冻结核心数据模型。
3. **中文《大水将至》（15-20%）**：定位结构压力测试，只转译一卷或 8-12 章，不为适配大改引擎。
4. **M3 裁定：暂停完整开发。**只允许支撑真实连载的最小滚动规划。20-30 章数据后再定 M3A/M3B 范围。

## 五、给月华的尖锐问题

> **如果 story-forge 最终证明能让小说更一致、更少泄底，却让你每章多花一倍时间、写作冲动被章节卡和审批流程耗尽，你是否愿意承认它作为「创作产品」失败，而不是继续把自己训练成适应系统的人？**

最可能的死法不是机器写不好，而是你为了证明系统有效，不断替它补写、补判断、补状态、补审美——系统的成功建立在你的超额劳动上。那不叫引擎成功，那只是把作者变成了隐藏基础设施。

## 最终裁定案

1. 项目继续，核心方向不改
2. 冻结检测器对抗和非必要功能扩张
3. M2 必须补异常路径与权威一致性验收，不能凭变更说明放行
4. 暂停完整 M3，以英文真实连载作为下一道投资门
5. 「作者分钟/千字」列一级指标
6. 若 20-30 章后不能证明质量提升大于流程成本，收缩为「正史状态管理+信息投影」工具，不再追求全流程写作操作系统

最大的优点是它曾敢于让实验推翻自己的预设。现在需要再次做到：**不要让已经投入的架构，替尚未获得的产品证据发言。**
