## 〇、结论先行

**方向成立，病根诊断不完整，按现有构想直接开工有 50% 概率做出一个"昂贵的拟真生活流模拟器"。**

三条核心判断：

1. **防火墙能防的是"叙述者泄底"，防不了"生成习惯性泄底"，也产生不了张力本身。** 泄底有两个来源：上下文可见性（防火墙可治）和 LLM 被 RLHF 出来的叙事习惯（开头埋的悬念结尾必回收、叙述者忍不住上帝腔）。第二个来源防火墙治不了，写作 agent 不知道真相，照样会自造伏笔并自我暗示。张力则来自另一处：戏剧反讽要求"有人知道秘密并表演"，纯隔离只会让写作 agent 写出没有质感的悬念。**隔离解决的是"别知道"，戏剧要的是"知道但要藏"——这是两件事，构想目前把它们混成了一件。**
2. **这个架构唯一能成立的分工线是：形状由事件 agent 控制，质感由角色 agent 涌现。** generative_agents 的检索打分（recency/relevance/importance）全是角色视角权重，没有任何读者视角的戏剧维度，它的记忆检索在代码层就注定了生活流。所以绝不能指望角色模拟涌现出故事，必须有外部的张力曲线强约束。拟真与叙事之争的解不在取舍，在这条分工线上。
3. **最小原型必须是对照实验，不是功能 demo。** 验证"防火墙防泄底"唯一干净的方法是同一骨架跑"有墙/无墙"两组，度量泄底率、冲突率、张力曲线三个数。设计见问题四，判定标准可证伪：若两组泄底率无显著差异，或实验组张力显著塌掉且钩子指令补不回来，核心假设即被证伪。

一句话：**立项通过，但要求先跑问题四的三组对照实验，用数据裁决病根诊断，再决定四路分工的完整版怎么建。**

## 一、逐题回答

### Q1：真正瓶颈会出现在哪里？

**瓶颈不在协调成本，在"暗账冲突裁定权"与"秘密的表演性泄露"这对矛盾上。** 分三层说：

**表层（可控）：协调成本。** 四 agent 加角色 sub agent，每章 token 是单 agent 的三到六倍。但注意防火墙其实省 token：写作 agent 上下文里没有暗账，比全知模式更小。净成本未必上升，值得在原型里量化，不构成否决项。

**中层（架构级）：泄底风险换成了冲突风险。** 写作 agent 看不到"管家是凶手"的暗账，完全可能独立写出管家毫无破绽的热心肠戏份，到回收章读者感觉被骗而非被惊艳。这就需要一个"全知审计员"同时看见正文与暗账做冲突检查。注意这个角色存在本身就说明：**防火墙防的是生成路径上的泄漏，不是系统级信息不对称**——系统里永远有一个上帝视角，问题只是它站在哪、结果怎么脱敏回传（见"额外发现"第 2 条）。ainovel-cli 已经预演过这个问题的机械化版本：`tools/commit_chapter_test.go` 里锁死的"拒绝前向伏笔引用"（重写早期章节时账本里躺着后续章节的伏笔，直接拒绝），说明全知账本对写作者的污染他们也撞过，只是解法用了机械校验而非隔离。

**深层（叙事级，真正的死穴）：角色 agent 的三难。** 设管家是凶手这条暗账：

- 角色知道自己是凶手 → 秘密通过它的"表演性线索"（言行细节）泄露给写作 agent 和读者，防火墙在角色这层漏了；
- 角色不知道 → 它的行为自然但与暗账矛盾（真好人演不出凶手的微妙破绽），"感到不对劲"这种戏剧反讽的质感只能靠写作 agent 撞运气写出来；
- 导演强制角色"演出破绽" → 角色 agent 的自主性名存实亡，generative_agents 的记忆流白搬，退化为提线木偶。

这个三难没有完美解，只有参数化解：**"泄露率旋钮"**——事件 agent 下发守密强度参数，控制秘密通过角色行为外溢的速率。守密太严无张力，太松则泄底。这个旋钮是整个项目最需要实验标定的叙事工程参数，比防火墙本身更关键。converse.py 的对话生成（`generate_one_utterance`，说话与是否结束同一次调用决定、无任何外部节奏控制）恰好是天然的实验场。

**拟真≠叙事担忧的正面回答：** 会涌现生活流，除非张力曲线由外部强加。证据在代码里：retrieve.py 的检索打分 `recency_w×recency×0.5 + relevance_w×relevance×3 + importance_w×importance×2`，三个维度全是角色主观视角（recency_decay=0.99、poignancy 由角色情绪强度打分）。角色只记得对自己重要的，不记得读者期待的。这不是实现缺陷，是目标函数错位——社会模拟的目标函数里根本没有"读者"这个变量。所以角色模拟只该负责"对白质感、行为可信度、记忆连续性"，节奏、悬念、回收时机必须由事件 agent 的张力曲线外部压上来。

### Q2：信息防火墙怎么落地最干净？

**结论：工具层权限过滤为主体，静态白名单做骨架，导演动态裁定只做内容级例外，绝不碰权限级。** 三者不是三选一，是分层：

1. **静态配置管"谁能看哪个 store 区"**。可审计、可 diff、可单测，防火墙规则本身进 git 版本库——"防火墙规则是这个项目真正的创作对象"（README 原话），那就该像代码一样被 review。
2. **工具层过滤管"每次调用实际返回什么"**。这是主体，而且 ainovel-cli 的结构几乎是现成的：信息已经全部通过工具进出（`novel_context` 单点注入、`read_chapter` 按需拉正文、`commit_chapter` 结构化落事实），`novel_context_builders.go` 已经按 writer/editor/architect 分别构建不同 envelope。改造点只是把"按 agent 身份构建"升级为"按 agent 身份过滤读数"：同一个 `LoadActiveForeshadow()`，writer 调用方拿到脱敏视图（只有"本章可埋钩子"），审计员拿到全量。不需要发明新机制。
3. **导演动态裁定只做内容级**："这一章埋哪个钩子、守密强度调多少"可以动态；"谁能看暗账"永远不交给 LLM 决定。动态权限 = 可见性本身可被 prompt injection 污染且不可复现，防火墙的价值恰恰在于它是机械的。

两个必须做对的工程细节：

- **泄密面审计日志**：每次 agent 调用的完整输入可重放、可 diff，"这本账谁在哪个 chapter 看过"可追溯。ainovel-cli 的 Checkpoints 事件流模式可直接复用。没有这个，防火墙形同虚设——你无法证明没漏。
- **错误信念要主动构造，不能靠"不告诉"**：generative_agents 的 scratch.py 有人格分层（L0 innate / L1 learned / L2 currently），Story Forge 的角色底板应加一层"持有的信念表"，错误信念写"错的版本"（管家：我护主心切，问心无愧），而不是留空让模型推理时自行补出真相。reflect 机制（重要性累积触发反思）正好可以挂"信念的形成、强化与瓦解"。

### Q3：参考仓库的借鉴与改造清单

**ainovel-cli——原样借鉴：**

- `internal/flow/router.go` 的纯函数路由骨架：State 显式声明全部事实、Instruction 输出、返回 nil 的明确语义、查表决策与语义决策分离。防火墙系统的调度必须确定性，这套直接抄。
- `domain/review.go` 的伏笔数据结构（ForeshadowEntry 的 planted/advanced/resolved 状态机 + ForeshadowUpdate 增量）与 `revision/projector.go` 的全量重放重建：暗账的生命周期管理、孤儿伏笔检测、"推进未知伏笔"报错、重写保 plant（issue #112）这些踩坑成果全部保值，只改归属——台账从 Writer 可见挪进事件 agent 私有区。
- `agents/guard/subagent_guards.go` 的 checkpoint + StopGuard 模式：流程纪律在框架层强制（end_turn 前查必需步骤的 checkpoint，连续空转升级终止）。防火墙合规同样适用：写作产出命中暗账语义近邻即机械拦截，不靠 prompt 自觉。
- 六步流程的信息架构："正文与事实分离、事实结构化落盘、正文按需拉取"。这是防火墙能落地的前提——信息有明确的流转关卡，才有过滤点。
- `editor.md` 七维评审中"伏笔健康（超 5 章未推进）"与"钩子质量"两个维度的量化思路，作为读者模拟器的指标起点。
- 收官纪律（finale 注入"不再新开长线"）：伏笔生命周期末段的调度刚需，事件 agent 的职责表里要有。

**ainovel-cli——必须按防火墙改造：**

- `tools/novel_context_builders.go`：全项目的改造主战场。现状是所有 envelope 从同一个全知 store 读数（`LoadActiveForeshadow()` 的结果直接进 writer 的 `episodic_memory.foreshadow_ledger`），prompt 里那句"不编造没有发生的事实"就是全部防线。这是"全知+行为约束"模式，Story Forge 要换成"受限信息+自然行为"，两者互为镜像。
- `tools/plan_chapter.go` 的契约字段：`forbidden_moves` / `required_beats` / `hook_goal` 这套叙事张力的工具化表达非常好，但**填表人要换**——现状是 Writer 自填自守，防火墙世界里应由事件 agent 下发，Writer 只执行。契约的字段设计原样保留。
- Editor 的一致性检查：editor 全知没问题，但它对 Writer 的返工反馈（rewrite_brief 模式）要做最小泄露脱敏，见"额外发现"第 2 条。
- `agents/ctxpack/strategy.go` 的摘要压缩：摘要是"有损但对称"，防火墙要"无损但不对称"。不能指望靠摘要防泄底——摘要完全可能恰好把伏笔压缩成一句显眼的话。摘要解决长度问题，不解决可见性问题，两套机制不可互替。

**generative_agents——原样借鉴：**

- `cognitive_modules/retrieve.py`：一百来行、逻辑干净的三维打分检索，作为角色 agent 的"亲历记忆"引擎。注意它的权重 gw=[0.5,3,2] 本身就是为拟真调的，作者自己注释说未来该学习——不要学它，保持角色视角，读者维度从外面压。
- `cognitive_modules/converse.py` 的 agent_chat_v2：双角色轮流各生成一句、各自检索各自私有记忆、互相看不到对方的检索结果与意图摘要。**这就是"角色互不知秘密"的现成实现**，information firewall 在 agent 间这层已经有学术先例，Story Forge 的增量在"导演层"和"作者层"，这要心里有数。
- reflect 机制 + scratch 的人格分层（前面说过，错误信念挂点）。
- "事件覆盖计划"的机制骨架：计划未分解部分在新事件发生时直接作废。方向反转后可用——不是角色日程被打断，是导演事件打断了角色惯性。

**generative_agents——必须改造：**

- `cognitive_modules/plan.py` 的日程规划思维：daily_req / hourly schedule 是生活流之源。角色的 plan 必须被事件 agent 的本章命运约束，角色规划自己的日常，命运之手负责让意外砸进去。
- converse 的无导演对话：最多 8 轮硬编码、结束与否由说话者自己判断、没有场景目标。改造：每场戏注入张力目标（导演下发）+ 结束判定权上收。
- importance 的 poignancy 打分（角色情绪强度决定记忆权重）：关键伏笔场景会被角色当日常琐事淡忘。可在事件入记忆时由导演补打一个"dramatic weight"，角色自己不感知这个权重。

### Q4：最小可行原型长什么样？

**先说原则：要验证的是"防火墙防泄底"这一件事，每个多余组件都会污染归因。** 所以我反对在最小原型里上角色 sub agent 和设定 agent——那是第二、第三个实验。README 阶段 3 预设的"双角色对手戏"对于单变量验证也偏大。

**组件（4 个 agent + 1 个 store）：**

- **事件 agent**（持暗账）：输入故事骨架与当前进度，输出每章的钩子指令、forbidden_moves、守密强度。暗账 3 条左右，预定回收章号。
- **写作 agent**（防火墙内）：可见=世界观公开设定、角色公开人设卡（不用 sub agent，静态卡）、已发布正文、事件 agent 的指令。不可见=暗账全文。
- **读者模拟器**（只读正文）：逐章输出"此刻猜到的可能真相列表 + 置信度 + 每条猜测的证据句引用"。
- **全知审计员**（读正文+暗账）：比对冲突，输出脱敏后的 forbidden_moves 增量。

**骨架直接用 ainovel-cli 的 Go 工程**：Router/Store/工具协议/guard 全现成，改动集中在 novel_context_builders 的身份过滤 + 事件 agent 的暗账 store。Python 起家看似贴近 generative_agents，但那个库没有引擎骨架，得自己补 Router 和落盘协议，不划算。

**实验设计（这是原型的灵魂）：三组对照，不止两组。**

| 组 | 写作 agent 上下文 | 检验什么 |
|---|---|---|
| A 全知组（现状） | foreshadow_ledger 全量注入（= ainovel-cli 模式） | 基线泄底率 |
| B 防火墙组 | 只见钩子指令 | 防火墙的净效果 |
| C 无账组 | 无暗账、自由写 | **病根检验：习惯性泄底是否存在** |

C 组是任务书没要求但我坚持要加的：若 C 组读者模拟器照样"提前猜中"写作 agent 自造的伏笔（自发暗示→自我回收的俗套循环），则证明泄底至少部分源于生成习惯而非信息可见，防火墙只是必要条件，还得配叙述纪律层。C 组顺手且便宜，不加是浪费。

**度量（没有度量的原型是 demo 不是实验）：**

1. **泄底率**：读者模拟器各章猜测命中暗账真相的比例与章号分布。预期 B < A，且回收章"惊讶度"（猜测置信度曲线在回收章的跳变）B > A。
2. **冲突率**：审计员拦截次数/章。预期 B > A——这是防火墙的代价，必须量化出来摆上台面。
3. **张力曲线**：读者模拟器逐章输出"想读下一章的欲望 1-10"。**若 B 组曲线整体塌掉（写作 agent 不知道真相就写不出悬念质感），防火墙在叙事上得不偿失**，这是要诚实面对的第三种失败模式。

**规模与成本**：单章 2000 字 × 12 章 × 3 组 × 5 次重复 ≈ 千次级 LLM 调用，跑得起。温度固定、骨架固定，变点唯一。

**可证伪判定标准**：
- B ≈ A（泄底率无显著差异）→ 防火墙无效，驳回核心构想；
- B 张力显著低于 A 且钩子指令救不回 → 隔离产生"信息真空"，需要转向"分层可见"（见额外发现第 1 条）；
- B 泄底率显著低、张力不塌、冲突率可控 → 立项假设成立，进入角色 sub agent 实验。

### Q5：最可能错的一个假设？

**"病根是所有信息在同一上下文里、没有信息隐私"这个诊断本身。**

反证路径：LLM 在完全不知道结局的单章续写任务里，同样表现出"写作习惯性剧透脸"——开头悬的念结尾必收、叙述者上帝腔、把伏笔当成急着交作业的暗示。这种泄底是训练分布的属性（RLHF 奖励了"结构工整、首尾呼应"的文本），不是上下文知识的属性。写作 agent 不含暗账，照样会自造一个"管家有秘密"并两章内自我揭穿。防火墙对这类泄底零作用。

之所以说是"最可能"错而不是"必然"错：信息可见性确实会加重病情（全知 writer 明知暗账时的暗示冲动有 ainovel-cli 需要用 forbidden_moves 和前向引用校验去压的痕迹），两层病因大概率叠加存在。但配比未知，而配比决定药方——若习惯性泄底占大头，工程重心就该从"隔离"转向"叙述纪律"（视角锁死、信息释放节奏规则、悬念最小暗示量约束），防火墙退居辅助。

Q4 的 C 组实验就是给这个假设的裁决法庭，这也是我坚持加它的原因。第二个候选假设（供参考）："信息隔离能产生张力"同样可疑——希区柯克的炸弹桌下定理要求观众知道、角色不知道，张力的产生恰恰依赖某处"知情"，纯隔离给出的是信息真空而非悬念。两问在 B 组张力曲线上一并裁决。

## 二、额外发现的问题

1. **"分层可见"可能是比"二值可见"更对的设计。** 戏剧反讽的正确结构是：写作 agent 知道"这里有个秘密要藏"，不知道"秘密是什么"。钩子指令应分两层：效果指令（写一个让读者不安的细节）优先于内容指令（写与父亲旧仇相关的物件），内容指令只在效果指令写不出质感时升级使用。信息量最小化应成为防火墙的语法学，"全知/无知"的二分太粗。
2. **审计反馈通道是防火墙上最窄也最脆的关。** 审计员发现冲突后回传给写作 agent 的任何话都在携带信息："避开管家的动机方向" ≈ 泄露管家有问题。极端情况下的正解是反向的：**让事件 agent 修改暗账去迁就已写正文**。暗账必须是"活的台账"（持续微调适配正文演化），不能是前期锁死的圣经——否则每章都在为十二周前的决定还债。这一条建议进架构原则。
3. **读者模拟器自带分布偏差。** 它也是 LLM，会猜中"任何 LLM 都会猜的俗套"（管家=凶手是文化先验），导致泄底率虚高。缓解：多个不同温度/人格的读者模拟器投票取中位；或退一步只做"证据句标记"（这句是否构成暗示）不做真相预测，证据句标记可对照暗账语义近邻半机械化，更客观。读者模拟器的结果只回传事件 agent，绝不过写作 agent。
4. **converse.py 的一个隐藏红利**：角色互不知秘密已有现成实现，秘密的"表演性泄露"可以自然涌现（角色记忆检索命中秘密时说漏嘴的质感远好于导演指定）。但泄露率必须可调——守密强度参数应进入事件 agent 的输出 schema（见 Q1 深层三难）。
5. **成本账可能比直觉好看**：防火墙让写作 agent 上下文变小（无暗账、无全量台账），单次调用便宜于全知模式；贵在多 agent 的调度与审计轮次。净成本建议在原型中一并统计，别凭直觉拍。
6. **一个流程级风险**：ainovel-cli 的 guard 证明流程强制要靠框架层 checkpoint，同理，防火墙的合规检查（写作产出不得命中暗账语义近邻）也必须机械拦截在 commit 前，不能指望写作 agent 自觉或事后审计。拦截器需要暗账语义指纹（embedding 近邻阈值），这是原型里唯一需要新写的"检测算法"，建议早做、做成独立可测的纯函数。

## 三、置信度自评

| 判断 | 置信度 | 依据与可证伪条件 |
|---|---|---|
| 防火墙工程落地方式（工具层过滤为主） | 高 | ainovel-cli 代码结构直接支持；若 novel_context 身份过滤实现遇到结构性障碍则降级 |
| 拟真≠叙事、需要外部张力曲线 | 高 | generative_agents 检索目标函数无读者维度（代码实证）+ 叙事学常识；B 组张力曲线可直接检验 |
| 泄底有"习惯性"成分、病根诊断不完整 | 中 | 来自对 LLM 写作分布的观察，未经本系统实验；Q4 的 C 组一跑便知 |
| 角色三难与泄露率旋钮 | 中高 | 从 converse 机制推出，但泄露率的可控范围未经标定 |
| 最小原型设计（三组对照+三度量） | 中高 | 实验设计逻辑自洽；读者模拟器的噪声水平可能被低估，落地时备好退化方案（证据句标记） |
| 借鉴/改造清单的文件级判断 | 高 | 逐一读过所列文件 |

**总体立场**：不驳回。立项通过，但附带硬性条件——先跑 Q4 的三组对照实验，用数据裁决病根配比与张力代价，再投入四路分工的完整建设。防火墙是必要条件的概率很高，是充分条件的概率很低；把"防止泄底"和"产生张力"拆成两个独立验收指标，是这个项目不把自己做成昂贵玩具的第一道保险。
